# Deep Learning for Table Tennis Analysis

## Context and Objective

In professional match videos, tracking provides the ball's 2D position in the image, frame by frame. However, it does not provide its depth: a single point in the image corresponds to an entire line of possible 3D positions. Only bounces on the table resolve this ambiguity, since the ball is then at a known height.

The goal is to estimate, for each shot, two 3D positions:

the ball's position at the moment of impact (where the player strikes the ball);
the ball's position as it crosses the plane of the net (with what clearance it passes over the net).

The 3D coordinate system has its origin at the center of the table, at ground level. The x-axis runs along the length of the table, meaning that the plane of the net is defined by x = 0.

The ultimate goal is to use these two positions to estimate, in real time, the probability of winning the point.

No 3D measurements are available from actual matches. The idea is therefore to rely on the physics of ball flight: we simulate a large number of trajectories whose 3D positions are known, project them onto the camera's image plane, and train a neural network to learn the inverse mapping (2D → 3D).

## Methodology and Progress
* Determine the camera projection model (how a 3D point maps to an image point)
* Simulate a large number of known 3D trajectories and project them into 2D
* Segment real-match tracking data so that it has the same structure as the simulated trajectories
* Train a 2D → 3D neural network, then evaluate it on real matches
* Estimate the probability of winning the point from the reconstructed 3D positions

## Simulating Trajectories to Build the RNN Training Dataset

### Generating 3D Trajectories

Trajectories are generated by integrating the equations of motion of the ball between two contacts (racket or table), using a fourth-order Runge–Kutta (RK4) scheme with a fine time step. Three forces are taken into account:

gravity;

aerodynamic drag (air resistance, quadratic in velocity);

the Magnus force, caused by the ball's spin (topspin, backspin, and sidespin).

Each trajectory starts from a randomly sampled initial state: impact position within the playing area, velocity, direction, and spin about all three axes. The physical coefficients are also varied slightly from one trajectory to another to avoid relying on a single set of parameter values. Only realistic trajectories are retained: they must clear the net and bounce on the opponent's side of the table.

The 3D positions are then sampled at the video frame rate and projected using the camera model to produce 2D trajectories that have the same characteristics as real tracking data.

### The Camera Model: Projecting Trajectories into 2D

The camera model links the simulated world (known 3D positions) to the real world (2D positions only). The broadcast camera is assumed to remain the same across all matches, and zoom and other disturbances are disregarded. It is calibrated once using reference points with known dimensions (table corners and net), and then validated against additional known points that were not used during calibration, to check that they are projected to the correct image locations.

This step is critical: if the virtual camera used in the simulation differs from the real camera, the network will learn an incorrect 2D → 3D mapping, introducing a systematic bias that training cannot correct. Since the camera is positioned far from the table, perspective effects are relatively weak. Depth is therefore the least constrained dimension by the image and the one most sensitive to calibration errors.

### Validation (Validation Code)

A separate validation script is used to assess the realism of the simulated trajectories. It overlays them with real trajectories obtained from tracking data to check whether the simulation (physics + projection) accurately reproduces what is observed in actual matches.

The final dataset consists of thousands of trajectories, to which Gaussian noise is added to simulate the measurement uncertainty inherent in real-match tracking data.

## The Neural Network

### The Problem

This is a supervised sequence regression task: the input is a sequence of 2D positions (x_px, y_px), with variable length, and the output is the corresponding 3D position (x_m, y_m, z_m) at each frame. Training minimizes the mean squared error (MSE) between the network's predictions and the ground-truth 3D positions from the simulations. The error is measured in centimeters, separately for each axis.

### Why a Bidirectional LSTM?

LSTM: a network with memory that processes the sequence frame by frame, retaining the information that matters. This is essential here: an isolated 2D position is insufficient to recover depth. It is the shape of the entire trajectory that provides the necessary information (gravity provides the scale, while table bounces provide an anchor).

Bidirectional: the network processes the trajectory in both directions, allowing the depth estimate at any given frame to rely on both past and future information (for example, the subsequent bounce). Since trajectories are reconstructed offline, this is perfectly acceptable, and it has proven to deliver by far the largest performance improvement.

### Training and Network Optimization

**Trajectory-level split (70 % training / 15 % validation / 15 % test)**: no trajectory is ever split across different subsets, ensuring that the test set genuinely contains previously unseen trajectories.

**Input and output normalization, computed using the training set only**: brings x, y, and z to comparable scales (otherwise, x, which ranges over ±2.9 m, would dominate z) and prevents information leakage into the test set. Errors are subsequently converted back into centimeters.

**Variable-length sequences: zero-padding + packing**: trajectories range from 12 to 83 frames. Packing prevents the LSTM from processing padding zeros, which is particularly important for a bidirectional network.

**Masked loss function**: the MSE ignores padded frames, ensuring that only actual frames contribute to the error.

**One 3D output per frame**: the network reconstructs the entire 3D trajectory, from which the relevant positions (at impact and at the net) can then be extracted.

**Adam optimizer**: adaptively adjusts the learning rate for each parameter. It converges quickly and is relatively insensitive to hyperparameter tuning, making it a good default choice for an LSTM.

**Gradient clipping**: limits the gradient magnitude at each update to prevent exploding gradients (which can cause training to diverge and produce NaN values).

**LSTM gates**: these, rather than gradient clipping, address the vanishing gradient problem. This is the main reason for using an LSTM instead of a standard recurrent neural network, particularly when dealing with longer sequences.

**Early stopping**: validation error is monitored during training, which stops when performance no longer improves. The best-performing model is then restored. This helps prevent overfitting while reducing computational cost.

**Baselines**: two reference models are used to assess the network's performance: a mean-value predictor and a feedforward network without memory that processes each point independently.

**Sanity check**: the network must be able to overfit a very small batch of trajectories (error ≈ 0). Otherwise, there is likely a bug, and there is no point in tuning hyperparameters until it has been fixed.

### Hyperparameter Selection

To identify the optimal neural network architecture, several networks with different configurations are trained and compared, retaining only the one that minimizes the error function while keeping computational time reasonable.

Experiments were conducted on a subset of 2,000 trajectories (maximum of 40 epochs, with early stopping), changing one parameter at a time, in order of expected impact: network directionality → learning rate → model capacity (number of layers × number of neurons).

The error plateaus as early as two layers: the largest network (3 × 128) provides only a marginal improvement despite requiring 3.5 times as much computation. We also observe that the error along the y-axis remains around 4.6 to 5 cm, regardless of network size. This indicates that model capacity is not the limiting factor in depth estimation.

The following configuration was therefore selected:

* Type: Bidirectional LSTM
* Layers: 2
* Hidden units per layer: 64
* Optimizer: Adam, learning rate 3e-3
* Batch size: 32
* Gradient clipping: 1.0
* Early stopping: patience of 10 epochs (maximum of 100 epochs)
